## Next implementation boundary

Source audit confirms `AppendTaskMergeOperationCommand` owns conflict history while ordinary task writes still use the legacy object snapshot path. Do not generate operations from a full submitted object unless the caller proves which version it read. The following mutation work must preserve intent and commit all effects through the existing SQLite actor transaction.

- Local canonical task edits enter through `service/runtime/objects.rs::upsert_object` and `LocalCoreTaskWrite::execute`; the object projection, HLC, receipt, and snapshot committed-feed entry are committed in one SQLite actor transaction.
- The first mutation-seam phase is complete (commits `98641825` and `6f205e3c`): local canonical writes/deletes, legacy `todo` writes/deletes, and inbound task snapshots/deletes all pass through `TaskMutationSession` in `application/task_mutation.rs`. Compatibility commands do not use `LocalCoreTaskWrite`, but they already use the shared transactional seam. This preserves existing projection, receipt, link, and feed behavior while generation remains disabled. The seam is not yet operation-aware and does not itself produce merge operations.
- Inbound full snapshots and local writes now hit the bootstrap fence through the shared task mutation seam. Keep the compatibility `todo`, tombstone, and direct entity paths covered by the same rejection contract.
- Safe sequence: (1) converge canonical, legacy, and delete task writes on one transaction seam with generation disabled — complete; (2) add authenticated operation delivery and inbound apply with separate per-peer progress — complete; (3) atomically fence legacy writes for operation-enabled tasks — complete; (4) omit merge-owned projections from generic initial and live feeds — complete; (5) make the shared task mutation transaction emit and materialize typed operations; (6) enable generation only after end-to-end tests prove local write, peer delivery, restart, and old-peer refusal. Do not create a mixed-mode window where a projection or peer can lose stored variants.
- Current accepted storage shape refines step (2): keep a dedicated operation journal and peer cursor rather than extending the coalescing committed feed. Operation positions are local delivery indexes, never causal order. Capability advertisement remains disabled until operation apply and delivery handlers exist.
- Outbound progress shape: an authenticated peer prepares one bounded merge batch through an actor command that checks the current policy, reads the immutable journal page, and persists the exact in-flight range atomically. The ACK names that batch and advances only its contiguous end. On policy identity change, keep the acknowledged position and invalidate only the pending batch; an excluded peer advances nothing, and re-enabling resumes from its last ACK. This makes journal selection and retry state atomic; transport still must recheck policy before sending.
- The owner clarified receiver policy: a device's type/content selection controls what it receives. Excluding a category stops transfers to that device and preserves local copies; other selected devices can still receive them. Adding a category back requires backfill. This policy is separate from merge history and deletion semantics.
