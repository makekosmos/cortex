# ARK typed-operation ownership map

Snapshot: worktree `ark-stage2`, HEAD `3bf8cbb8025232137bcbad7df85f3428ff80391c` (20 October 2026). Inventory source: `.audit/ark-core-storage-census-2026-10-19.md`. This map follows each inventory entry from its `DbCommand`/`DbQuery`/`DbMaintenanceCommand::execute` to direct Store calls and named helpers. It records the current split, not an endorsement that every remaining Core SQL statement belongs in Core.

## Execution and exposure conventions

`DbCommand` enters the single Core scheduler and executes in one immediate SQLite transaction through `ark_store::writer::SqliteWriter::immediate`; Store owns that connection and begin/commit/rollback. `DbQuery` executes against a read connection in a deferred transaction. `DbMaintenanceCommand` holds the exclusive maintenance connection behind the Core maintenance barrier; restore delegates the lifecycle to Store. The scheduler implementation is `core/crates/ark-core/src/db/command/executor/actor/task.rs::{TypedCommand::run,TypedMaintenance::run}` and its reply is published after the writer slot is released (`settle`).

All 69 inventory operations retain Core SQLite exposure today: their public-to-command boundary is implemented as Core DB operation types and receives a `rusqlite::Transaction`, `Connection`, or maintenance `Connection`; several call Store adapters with that borrowed handle, while others still issue SQL in Core or Core-owned helpers. Store does not open a second database or commit these nested operations. “Reply only” below means no independent post-commit side effect was found in the operation implementation; the result is delivered after commit to its caller, which may perform subsequent Engine/sync work. Where a behavior depends on a caller, that dependency is named rather than counted as an operation-side effect.

Savepoint notes identify explicit nested savepoints in the direct call path. “No operation-local savepoint found” means the outer transaction is the visible boundary; it does not imply that every deeper adapter has been exhaustively proven free of internal savepoints. `Core SQL` marks an ownership seam still resident above Store. Policy descriptions identify the current authority; they do not infer that a policy is pure domain logic where code shows otherwise.

## Boundary findings from the map

- The census’s 69 operations do not imply 69 Store migrations. Many are Core policy/composition over Store capabilities, as the accepted boundary specifies. The strongest residual Core persistence seams among these operations are the Core task-merge helper facade (`db/task_merge`), canonical sync-apply savepoint/orchestration (`canonical_types/facades`), and integration read/admission composition (`db/integration_replication_*`). They should be scoped by function and SQL ownership before transfer.
- Savepoint ownership is split: Store has explicit operation-local savepoints for sync profile upsert, registry event pages, policy-bound entity/feed reads, feed pages/snapshots, usage migration, and delete-trashed. Canonical sync apply and canonical migrations retain Core savepoints by documented ownership choice. The outer transaction remains the single writer/reader transaction in all cases.
- `ark-core` SQLite exposure remains for all entries because the operation contract accepts rusqlite handles; Store APIs mostly accept those same borrowed handles, so no extra database/transaction is created. Removing that type exposure is a separate contract redesign, not achieved by the SQL extraction alone.
- Post-commit behavior is generally caller-driven. The writer publishes each reply only after releasing its slot; this map found no per-operation callback or event emitted from the transaction body itself. Returned commit/outcome/feed/session values are the handoff for subsequent work.
- Exact `Store SQL capability` calls are linked to Store modules named in each row. Abbreviated command source names in tables are relative to `core/crates/ark-core/src/db/command/commands/`; files named under `db/`, `application/`, `integration_replication/`, or `iroh_transport.rs` are relative to `core/crates/ark-core/src/`. Where the Core call is indirect through a backend/application session, the map marks the path as indirect or unresolved rather than inferring a Store-owned policy.
