# Замер скорости сборки Rust (2026-09-30)

Цель: получить честные цифры, прежде чем решать про новый Rust, `rust-lld` (KOS-264)
и nightly с параллельным фронтендом для локальной разработки. Релизы в любом случае
собираются на stable.

## Условия

- Машина: Ryzen 5 5600X (6 ядер / 12 потоков), 32 ГБ, C: — NVMe (Samsung 990 PRO),
  Windows 11 Pro 26200. Исключения Defender для папок сборки уже включены.
- Код: cortex `main` @ `94eb4530`, без локальных изменений.
- Команда во всех случаях одна: `cargo +<toolchain> build --workspace --all-targets`
  (debug-профиль, корневой workspace: `runtime`, `package-protocol`, `ark-core`).
  `manager-gpui` — отдельный манифест, в замер не входил.
- Перед каждым шагом скрипт ждал, пока на машине не останется чужих `cargo`/`rustc`.
- mbx 1.13.0, бюджет общего кэша 20 GiB.

## Конфигурации

|     | Toolchain                    | Линковщик       | Флаги          |
| --- | ---------------------------- | --------------- | -------------- |
| A   | stable 1.95.0                | MSVC `link.exe` | —              |
| D   | 1.98.1                       | MSVC `link.exe` | —              |
| B   | 1.98.1                       | `rust-lld.exe`  | —              |
| C   | nightly-2026-09-29 (1.101.0) | `rust-lld.exe`  | `-Z threads=6` |

Линковщик задавался переменной `CARGO_TARGET_X86_64_PC_WINDOWS_MSVC_LINKER`,
флаги — через `RUSTFLAGS`. В репозиторий ничего не коммитилось.

## Случаи

1. **clean** — пустая целевая папка, cargo напрямую через rustup, без mbx.
2. **incr-edit** — в той же папке добавлена одна функция в `runtime/src/focus.rs`,
   пересборка (типичный цикл «поправил → собрал / прогнал тесты»).
3. **no-op** — повторная сборка без изменений.
4. **mbx-prime** — первая сборка через mbx в новую папку (кэш для этой
   конфигурации ещё пуст; у A он был частично прогрет сборками этого дня).
5. **mbx-warm** — ещё одна новая папка через mbx с уже прогретым кэшем
   (сценарий «свежий worktree»).

## Результаты, секунды

|                                        |     clean | incr-edit | no-op | mbx-prime | mbx-warm |
| -------------------------------------- | --------: | --------: | ----: | --------: | -------: |
| A: 1.95 + link.exe                     |     174.4 |      48.5 |   1.7 |   158.2 ¹ |    131.6 |
| D: 1.98.1 + link.exe                   |     170.6 |      43.9 |   2.0 |     187.5 |    128.0 |
| B: 1.98.1 + rust-lld                   |     169.3 |  **26.8** |   1.2 |   169.2 ² |  167.5 ² |
| C: nightly + rust-lld + `-Z threads=6` | **158.4** |  **25.5** |   1.2 |   239.8 ² |  155.9 ² |

¹ Кэш уже содержал часть артефактов 1.95 (265 попаданий).
² mbx пропустил кэш целиком (599 из ~605 компиляций «bypassed»), см. ниже.

Размер целевой папки: без mbx 19–20 ГБ, через mbx около 13 ГБ.

## Выводы

1. **Rust 1.98.1 вместо 1.95** даёт немного: −2% на чистой сборке и −10% на
   пересборке. Обновление бесплатное, его стоит сделать.
2. **`rust-lld` — главный выигрыш для ежедневной работы:** пересборка после правки
   идёт 26.8 с вместо 43.9 с (−39% против D, −45% против A). В `--all-targets`
   линкуется много тестовых бинарников, и `link.exe` на них тратит основное время.
   На чистую сборку линковщик почти не влияет.
3. **nightly с `-Z threads=6`** даёт ещё −6% на чистой сборке и −5% на пересборке
   к B. Этого мало, чтобы уводить локальную разработку с stable.
4. **mbx 1.13 на Windows несовместим с `rust-lld`.** Любой линковщик, заданный
   через Cargo, mbx не может учесть в ключе кэша (`rustc codegen option is not
modeled by the cache adapter: linker`) и пропускает кэш. Не помогли ни
   `rust-lld.exe` в `PATH`, ни `MBX_LINKER=rust-lld` (`managed rust-lld selection
on Windows is not supported yet`), ни `MBX_LINKER=path:<rust-lld.exe>`
   (build-скрипты начинают искать `clang`).
5. **Прогретый mbx с `link.exe` экономит около 25%** на свежем worktree
   (128 с против 171 с). Больше не выходит: крейты самого workspace и их
   инкрементальное состояние пересобираются всё равно (77 промахов + 52
   incremental), а на NTFS reflink не работает, и артефакты копируются.

## Что это значит для решения

Выбор сейчас между двумя вариантами, совместить их нельзя до поддержки
rust-lld в mbx на Windows:

- **`rust-lld` без кэша mbx:** каждая пересборка на ~17 с быстрее, зато первая
  сборка нового worktree на ~40 с дольше и целевая папка на ~7 ГБ больше.
  Окупается уже со второй-третьей пересборки в worktree.
- **`link.exe` с кэшем mbx:** быстрее старт нового worktree и меньше места на
  диске, но каждая пересборка медленнее.

Nightly для локальной разработки не нужен.

Выводы:

1. Основное время `link.exe` уходило не на сам линковщик, а на полный debuginfo
   (PDB на ~20 ГБ) и на 52 отдельных тестовых бинарника, каждый из которых заново
   линковал весь engine. Убрав оба, H ускоряет пересборку в 3.2 раза, свежий
   worktree через mbx в 2.3 раза и уменьшает target в 3 раза.
2. `rust-lld` поверх H даёт ещё ~1.4 с на пересборке. Выбор «rust-lld или
   кэш mbx» из раздела выше после H почти ничего не стоит: `link.exe` + mbx.
3. Цена G: все интеграционные тесты крейта идут в одном процессе. Общее
   состояние процесса (переменные окружения, хуки отказов воркера, записи
   OS keyring, panic hook) должно закрываться общими блокировками — это
   сделано вместе с объединением.

Отдельно замерен полный `node runtime/scripts/test-lib.mjs --workspace` с
холодной целевой папкой (конфигурация E): `CARGO_BUILD_JOBS=1` — 1474 с,
`=6` — 529 с, `=12` — 498 с. Свободной памяти ни разу не было меньше 17.5 ГБ
из 32.

## Раунд 3: из чего состоит гейт (2026-10-01)

Полный `pnpm run check` после правки в `runtime/` — около 297 с. Из них
`test:rust` 230.5 с, `clippy` 23.7 с, `test:static` 20.4 с, Manager 17.1 с,
остальное около 5 с. Компиляция после правки: 17.7 с (`runtime/`), 21.5 с
(`ark-core`). Тестовая сборка engine (lib) — 16 с против 7 с у обычной: тесты
удваивают компиляцию того крейта, который правили. С чистого листа workspace
собирается за 155 с (iroh ≈ 8 %, наш код ≈ 22 %), Manager — 444 с (gpui).

Сами тесты под `cargo test` шли 157 с: бинарники запускаются по очереди, и
хвост каждого ждёт свой самый медленный тест (`engine it` — 80 с на 83 теста,
engine lib — 61 с на 984). Под cargo-nextest (процесс на тест, параллельно по
всем бинарникам) те же 1526 тестов проходят за 77–80 с. Тёплый
`node runtime/scripts/test-lib.mjs --workspace` целиком — 94 с (три прогона
подряд зелёные, 0 оставленных файлов в gate-tmp). Doc-тестов в workspace нет;
отдельный `cargo test --doc` занимает около 6 с и стоит в гейте, чтобы новые
не потерялись.

Время упирается в несколько тестов, которые ставят и запускают 25-мегабайтный
воркер в песочнице: `signed_catalog_bridge_runs_through_service` (55 с в общем
прогоне, 46 с отдельно), `fixture_workers_validate_protocol_and_fail_closed`
(37 с), `loopback_http_launch_lease_lifecycle_uses_signed_installed_package`
(31 с), `signed_bridge_worker_projects_real_ark_and_restarts_idempotently`
(21 с).

Что изменено:

1. Rust-тесты гейта идут через cargo-nextest (`.config/nextest.toml`). Тесты,
   которые делят OS keyring (фиксированные node id хостов), вынесены в группу
   с одним потоком: процесс на тест снимает защиту in-process мьютекса.
2. pre-commit гоняет только проверки на секунды: после правки в `runtime/`
   это brand, source-size и rustfmt — 4.6 с вместо ~4–5 минут; изменение,
   требующее полного гейта, запускает `check:fast` — 5.1 с. Clippy, тесты,
   runtime staging и Manager идут в pre-push; кеш планировщика не засчитывает
   быстрый прогон за полный.

## Как повторить

Скрипт замера лежал вне репозитория (`C:\mk\bench\bench.ps1`). Схема: для каждой
конфигурации выставить toolchain / переменные линковщика и `RUSTFLAGS`, затем по
очереди выполнить пять случаев выше с отдельными `CARGO_TARGET_DIR`; cargo без
mbx — `%USERPROFILE%\.cargo\bin\cargo.exe`, через mbx — shim
`%LOCALAPPDATA%\mbx\bin\cargo.exe`. Время — `Stopwatch` вокруг вызова cargo;
`cargo fetch` выполнялся заранее и в замер не входил. Раунд 2 — тот же подход,
скрипт `C:\mk\bench\bench2.ps1 -Config E..I` (патчи накладывались на рабочую
копию и откатывались после замера).
