# ARK write-flow census

This census records the write boundaries in Ark Core's database, service, schema, registry, and replication code. Local commands cover `core.task`, usage records, legacy, object, type, link mutations, Engine reset and deletion operations, and usage-log compaction. Read RPCs use sealed `DbQuery` types. A bounded writer actor owns the production SQLite connection and runs each database command in an immediate transaction. Queries use separate read connections and deferred snapshots.

Admission allows at most 128 active commands and queries or 64 MiB of admitted work. A command or query may use at most 16 MiB plus 4 KiB. Each source may hold at most 24 operations and 20 MiB, with at most 64 active sources. One source slot, 16 commands, and 16 MiB remain available for interactive work. One more source slot, 16 commands, and 8 MiB remain available for live sync. Backfill uses the remaining capacity. The scheduler weights interactive, live-sync, and backfill work, then rotates among eligible sources within each class. The writer census gate checks a reviewed allowlist of production path/category counts; it detects inventory changes but does not prove that a match is a live writer or identify its owner.

## Behavior tests

- `db/tests_sync/storage_backend_roundtrips.rs` and `storage_backend_tombstones_and_vectors.rs`: backend round-trips, invalid payload rejection, usage paging, deletes/tombstones, KV, and stored HLC.
- `db/command.rs`: sync read queries retain the backfill class and do not open a write transaction.
- `db/command/executor/admission.rs` and `db/command/tests/production_actor/`: aggregate command/byte limits, per-class capacity reserves, per-source limits, round-robin source fairness, maintenance barriers, lifecycle, and permit release.
- `db/sync/tombstone_history.rs` and `db/tests_sync/pending_objects_and_integrity.rs`: tombstone history and pending replay for unknown type versions.
- `service/tests/type_mutation_commands.rs`: type batch rollback and replay notification timing across commit/rollback.
- `db/tests_sync/canonical_object_transaction/`, `usage_sync_log_compaction.rs`, and `usage_sync_cursors.rs`: transactional object apply, compaction boundaries, cursor behavior, and relay convergence.
- `db/tests_sync.rs` exercises both adapter query variants, both command paths, context-peer binding, replay rollback, and retry after rollback.
- `tests/it/sync_round_trip.rs`: regular two-server and selective-profile replication.
- Local object behavior also has coverage in `service/tests/object_write_snapshot.rs`, `object_revision_compat.rs`, and `sync_lifecycle.rs`.

## Writer groups and current boundaries

| Writer group | Physical mutation and current boundary | Coupled metadata or exception |
|---|---|---|
| Local service mutation families: `service/runtime/{legacy,usage,objects,types}.rs` | Sealed commands run through `DbHandle` and commit one transaction on the existing shared SQLite connection. Lower-level CRUD helpers receive the command transaction. | Local upsert/delete metadata (version vector, tombstones, object sync versions) commits with the entity write. Broadcast and type replay notices follow successful commit. |
| Regular remote entity apply and reads: `sync_server_inbound.rs`, `sync_server_messages.rs`, `sync_client_start/connect_and_receive.rs`, `relay_impl_2.rs` → application-owned entity read/mutation ports and `PeerProgressPort` → typed `DbHandle` commands/queries → `db/backend/apply.rs` | Each entity apply runs in an immediate SQLite transaction through the adapter-owned mutation session. Each page query is independent; no shared snapshot spans page calls. | Entity state and supported HLC/tombstone/usage/canonical metadata are applied together. Authenticated page reads preserve peer identity and `SyncLive`/`Backfill` class at the storage boundary. KOS-420 persists committed changes and resumable feed progress; KOS-421 separates receipt and apply acknowledgements for negotiated peers. |
| Registry and pending replay: `service/runtime/types.rs`, `type_registry/`, `canonical_types/pending/`, `db/objects/` | Runtime type registration and type mutation use commands; replay helpers share the command or remote-apply transaction. Catalog and schema migration writes still use their existing SQLite boundaries. | Unknown type-version payloads can be retained and replayed after registration. Replay events publish only after the owning transaction commits. |
| Profiles and local metadata: `data_platform.rs`, `service/runtime/system.rs`, `db/command/commands/sync_mutation.rs` | Engine `set_sync_kv` submits a sealed Interactive command through `DbHandle`; profile upsert owns a savepoint, and game local-state writes are caller-owned or share a game-upsert savepoint. | `object_local_state` and sync progress/settings are not ordinary replicated entity payloads. Per-device selective profile controls projection. |
| Maintenance and reset: `db/load/all_data.rs`, `db/compact.rs`, `service/runtime/system.rs`, `service/runtime/usage.rs`, `db/command/commands/system_mutation.rs` | Engine `clear_all`, `delete_trashed`, bounded usage-log compaction, and restore use sealed `DbHandle` commands or maintenance operations. Reset, compaction, and restore use Maintenance; trash deletion is Interactive with its existing savepoint. | `clear_all` is not mapped to per-record delete semantics. It preserves system-locked type definitions and `usage_sync_heads`. Compaction is journal maintenance, not source-entity deletion. The actor enforces admission, lifecycle, shutdown, recovery, and maintenance barriers. |
| Bootstrap, schema, and migration: `db/open.rs`, `schema.rs`, `type_registry/`, `canonical_types/migration*/`, `canonical_types/core_task_rewrite.rs` | Schema initialization uses DDL and named savepoints, without one encompassing `open_db` transaction. Registry/migration runners use savepoints; `rewrite_legacy_tasks` uses `unchecked_transaction` after a backup. | Migration ledgers, archives, quarantine, pending-table rebuilds, compatibility columns, and persistent pragmas are not incremental sync writes. |

The direct mutation search used for this baseline was:

```sh
rg -n --glob '*.rs' --glob '!**/tests/**' --glob '!**/*_tests.rs' --glob '!**/tests_*.rs' '(execute(_batch)?\s*\(|INSERT\s+INTO|UPDATE\s+[A-Za-z_][A-Za-z_0-9]*\s+SET|DELETE\s+FROM|REPLACE\s+INTO|ALTER\s+TABLE|CREATE\s+TABLE|DROP\s+TABLE|INSERT\s+OR\s+REPLACE|INSERT\s+OR\s+IGNORE)' core/crates/ark-core/src/db core/crates/ark-core/src/service core/crates/ark-core/src/canonical_types core/crates/ark-core/src/type_registry core/crates/ark-core/src/data_platform.rs core/crates/ark-core/src/schema.rs
```

It produced 393 lines across 49 files in those roots, including test-only blocks embedded in production files that were inspected and excluded from the classification. Follow-up searches covered `transaction`, `unchecked_transaction`, pragma updates, and backup calls. `data_platform.rs` writers were classified. Sync clients, server handlers, and relay code delegate to the adapter paths above and remain separate protocol owners. This is a scoped source census, not a repository-wide proof. Classify new SQL and transaction APIs, each new `SyncEntity` constructor, and every ordinary apply caller against these groups. Preserve the observed `clear_all` subset and its exception behavior unless its product contract changes.

The extraction's SQLite behavior pin was `cargo nextest run -p ark-core storage_backend` (13 tests) before and after moving the modules. The full crate suite passes after the move; exact commands and exit statuses are in `.audit/modules-receipts.md`.
