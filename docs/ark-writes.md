# ARK write-flow census

This census records the write boundaries in Ark Core's database, service, schema, registry, and replication code. Local commands cover `core.task`, usage records, legacy, object, type, link, integration RPC mutations, Engine reset and deletion operations, and usage-log compaction. Read RPCs use sealed `DbQuery` types. A bounded writer actor owns the production SQLite connection and runs each database command in an immediate transaction. Queries use separate read connections and deferred snapshots.

Admission allows at most 128 active commands and queries or 64 MiB of admitted work. A command or query may use at most 16 MiB plus 4 KiB. Each source may hold at most 24 operations and 20 MiB, with at most 64 active sources. One source slot, 16 commands, and 16 MiB remain available for interactive work. One more source slot, 16 commands, and 8 MiB remain available for live sync. Backfill uses the remaining capacity. The scheduler weights interactive, live-sync, and backfill work, then rotates among eligible sources within each class. The writer census gate checks the reviewed production roots and matched 54 path/category counts after the cutover.

## Behavior tests

- `db/tests_sync/part1.rs`–`part2.rs`: backend SQLite round-trips, invalid payload/type rejection, usage paging, deletes/tombstones, KV, and stored HLC.
- `db/command.rs`: sync read queries retain the backfill class and do not open a write transaction.
- `db/command/executor/admission.rs` and `db/command/tests/production_actor/`: aggregate command/byte limits, per-class capacity reserves, per-source limits, round-robin source fairness, maintenance barriers, lifecycle, and permit release.
- `db/tests_sync/part3.rs` and `part5.rs`: pending replay and unknown-version preservation/replay.
- `service/tests/type_mutation_commands.rs`: package batch rollback and replay notification timing across commit/rollback.
- `db/tests_sync/part4.rs`, `part6.rs`, and `part7.rs`: direct adapter collection/apply, compaction boundaries, cursor behavior, and relay convergence.
- `db/tests_integration_replication_apply.rs` and `integration_replication/signed_sync_tests.rs`: signed authorization and atomic apply.
- `db/tests_integration_replication_adapter.rs` exercises both adapter query variants, both command paths, context-peer binding, replay rollback, and retry after rollback.
- `tests/it/sync_round_trip.rs`: regular two-server and selective-profile replication.
- Local object behavior also has coverage in `service/tests/object_write_snapshot.rs`, `object_revision_compat.rs`, and `sync_lifecycle.rs`.

## Writer groups and current boundaries

| Writer group | Physical mutation and current boundary | Coupled metadata or exception |
|---|---|---|
| Local service mutation families: `service/runtime/{legacy,usage,objects,types}.rs` | Sealed commands run through `DbHandle` and commit one transaction on the existing shared SQLite connection. Lower-level CRUD helpers receive the command transaction. | Local upsert/delete metadata (version vector, tombstones, object sync versions) commits with the entity write. Broadcast and type replay notices follow successful commit. |
| Regular remote entity apply and reads: `sync_server_inbound.rs`, `sync_server_messages.rs`, `sync_client_start/part03.rs`, `relay_impl_2.rs` → `StorageBackend` → typed `DbHandle` commands/queries → `db/backend/apply.rs` | Each entity apply runs in an immediate SQLite transaction. Read queries use the same connection without creating a write transaction. | Entity state and supported HLC/tombstone/usage/canonical metadata are applied together. Authenticated page reads preserve peer identity and `SyncLive`/`Backfill` class at the storage boundary. Pull cursor/vector persistence happens later and is not atomic with the entity commit. |
| Signed remote integration apply: `sync_server_inbound.rs` → `db/backend/adapter.rs` → sealed `DbCommand` and transaction-aware apply helper | `DbHandle` owns one immediate transaction for authenticated identity checks, authorization, replay reservation, and writes. Outbound validation uses a sealed `DbQuery` without a write transaction. | Separate from ordinary `SyncEntity` apply. The signed frame and command wrapper fit the 16 MiB transport limit and bounded command admission. |
| Registry and pending replay: `service/runtime/types.rs`, `type_registry/`, `canonical_types/pending/`, `db/objects/` | Runtime package registration and type mutation use commands; replay helpers share the command or remote-apply transaction. Catalog and schema migration writes still use their existing SQLite boundaries. | Unknown type-version payloads can be retained and replayed after registration. Replay events publish only after the owning transaction commits. |
| Profiles, external references, and local metadata: `data_platform.rs`, `service/runtime/system.rs`, `db/command/commands/{external_ref,sync_mutation}.rs` | `external_refs.upsert` and Engine `set_sync_kv` submit sealed Interactive commands through `DbHandle`; external-ref schema ensure and upsert share its immediate transaction. Profile upsert owns a savepoint; game local-state writes are caller-owned or share a game-upsert savepoint. | `external_refs`, `object_local_state`, and sync progress/settings are not ordinary replicated entity payloads. External-ref writes have no HLC coupling. Per-device selective profile controls projection. |
| Maintenance and reset: `db/load/part1.rs`, `db/compact.rs`, `service/runtime/system.rs`, `service/runtime/usage.rs`, `db/command/commands/system_mutation.rs` | Engine `clear_all`, `delete_trashed`, bounded usage-log compaction, and restore use sealed `DbHandle` commands or maintenance operations. Reset, compaction, and restore use Maintenance; trash deletion is Interactive with its existing savepoint. | `clear_all` is not mapped to per-record delete semantics. It preserves system-locked type definitions, integration/auth records, and `usage_sync_heads`. Compaction is journal maintenance, not source-entity deletion. Actor ordering and lifecycle barriers remain pending. |
| Bootstrap, schema, and migration: `db/open.rs`, `schema.rs`, `type_registry/`, `canonical_types/migration*/`, `canonical_types/core_task_rewrite.rs` | Schema initialization uses DDL and named savepoints, without one encompassing `open_db` transaction. Registry/migration runners use savepoints; `rewrite_legacy_tasks` uses `unchecked_transaction` after a backup. | Migration ledgers, archives, quarantine, pending-table rebuilds, compatibility columns, and persistent pragmas are not incremental sync writes. |
| Integration credentials and refresh coordination: `service/runtime/integration.rs`, `db/integration_replication_*.rs`, `db/command/commands/integration_admin.rs` | Node authorization, grants, refresh lease acquisition, and credential publication submit sealed Interactive commands; transaction-aware policy and persistence helpers run inside the `DbHandle` immediate transaction. | These operations are local integration coordination, distinct from signed replicated content. |

The direct mutation search used for this baseline was:

```sh
rg -n --glob '*.rs' --glob '!**/tests/**' --glob '!**/*_tests.rs' --glob '!**/tests_*.rs' '(execute(_batch)?\s*\(|INSERT\s+INTO|UPDATE\s+[A-Za-z_][A-Za-z_0-9]*\s+SET|DELETE\s+FROM|REPLACE\s+INTO|ALTER\s+TABLE|CREATE\s+TABLE|DROP\s+TABLE|INSERT\s+OR\s+REPLACE|INSERT\s+OR\s+IGNORE)' core/crates/ark-core/src/db core/crates/ark-core/src/service core/crates/ark-core/src/canonical_types core/crates/ark-core/src/type_registry core/crates/ark-core/src/integration_replication core/crates/ark-core/src/data_platform.rs core/crates/ark-core/src/schema.rs core/crates/ark-core/src/space
```

It produced 393 lines across 49 files in those roots, including test-only blocks embedded in production files that were inspected and excluded from the classification. Follow-up searches covered `transaction`, `unchecked_transaction`, pragma updates, and backup calls. `data_platform.rs` writers were classified; no production SQL writer was found under `space/`. Sync clients, server handlers, and relay code delegate to the adapter paths above and remain separate protocol owners. This is a scoped source census, not a repository-wide proof. Classify new SQL and transaction APIs, each new `SyncEntity` constructor, and every ordinary/signed apply caller against these groups. Preserve the observed `clear_all` subset and its exception behavior unless its product contract changes.

The extraction's SQLite behavior pin was `cargo nextest run -p ark-core storage_backend` (13 tests) before and after moving the modules. The full crate suite passes after the move; exact commands and exit statuses are in `.audit/modules-receipts.md`.
