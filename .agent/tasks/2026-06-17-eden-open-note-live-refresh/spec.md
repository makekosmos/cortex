# Eden: live-перерендер ОТКРЫТОЙ заметки при удалённом изменении

Дата: 2026-06-17
Классификация: FULL_LOOP (Eden editor internals + риск потери данных).
Ветка: feat/iroh-transport.

## Контекст / что уже работает

Sync (iroh) теперь доставляет изменения вживую и эмитит renderer-события:

- Backend при входящей peer-записи объекта эмитит `object_upserted`/`object_deleted`
  (с `id`, `type_id`) — так же, как локальная запись. (Сделано в ark-core
  `wire_relay_sync_events` on_change + `Request::UpsertObject`.)
- Eden подписывается через `edenApi.subscribeObjectChanges` /
  `kepler-api-shim.ts subscribeObjectChanges` (`products/eden/src/lib/`).
- На это уже реагируют список заметок и TaskRef NodeView (чекбокс/title
  live-обновляются).

## Проблема

Контент ОТКРЫТОЙ заметки (`useEdenStore().currentEntry`, рендерится в
`Editor`/`editor-cm/CmEditor.vue`) НЕ обновляется при удалённом изменении той же
заметки — пользователю приходится выйти и снова открыть заметку. Хотя событие
`object_upserted` с нужным `id` уже приходит.

## Цель

Когда приходит `object_upserted` для `id`, равного `currentEntry.value?.id`, и
изменение пришло ИЗВНЕ (не наш собственный autosave), перечитать заметку из ARK
(`window.api.loadEntry(id)`) и пере-гидратировать редактор — без потери данных.

## Жёсткие ограничения (НЕ нарушать — иначе data loss)

1. **Никакого self-feedback loop.** На ЭТОМ устройстве собственный autosave тоже
   эмитит `object_upserted` для того же `id`. Реакция на своё же сохранение
   приведёт к лишней пере-гидратации/сбросу курсора или к циклу. Нужно отличать
   удалённое изменение от своего:
   - вариант A: сравнить входящий `content_json` (из свежего `loadEntry`) с тем,
     что уже в редакторе/baseline — если совпадает, ничего не делать;
   - вариант B: трекать «мы только что записали этот id» (по таймстемпу/флагу
     вокруг autosave) и игнорировать ближайшее эхо;
   - выбрать наиболее надёжный для текущей архитектуры (предпочтительно A —
     content-equality, т.к. устойчиво к гонкам).
2. **Не затирать активный локальный ввод.** Если пользователь прямо сейчас
   редактирует эту заметку (редактор «грязный»/в фокусе, есть несохранённые
   изменения) — НЕ перезаписывать его текст удалённой версией. Поведение в
   конфликте: либо отложить применение до сохранения/потери фокуса, либо
   пропустить (и положиться на следующее открытие). НЕ делать молчаливый
   overwrite пользовательского ввода. (CRDT здесь last-writer-wins на весь
   объект, не посимвольный merge — посимвольный merge вне scope.)
3. **Сохранить позицию курсора/скролл при безопасной пере-гидратации**, насколько
   это поддерживает редактор. Если редактор не сфокусирован — просто заменить
   контент.
4. **Cleanup подписки** в `onBeforeUnmount`/scope dispose (universal never rule:
   нет addEventListener/подписок без cleanup).
5. Только UI-слой Eden. НЕ трогать ARK/sidecar/protocol. НЕ менять схему.

## Указания по реализации (ориентир)

- Точка подписки: разумнее всего в сторе `products/eden/src/store/eden.ts` (он
  владеет `currentEntry` и уже умеет `loadEntry`/`upsertEntryBaseline`/
  `ensureEntryCmSafe`), либо в корневом компоненте, который живёт весь lifecycle.
- Изучи как `currentEntry` гидратируется и как Editor отслеживает dirty/baseline
  (см. `upsertEntryBaseline`, `ensureEntryCmSafe`, autosave/handleSave в
  Editor/CmEditor и shim saveCoordinator). Переиспользуй существующие хелперы.
- Для `object_deleted` открытой заметки — корректно обработать (закрыть/очистить
  или пометить удалённой согласно текущему UX удаления).

## Acceptance

- При удалённой правке открытой заметки её контент обновляется в редакторе БЕЗ
  перезахода, и БЕЗ сброса/потери собственного несохранённого ввода.
- Собственный autosave НЕ вызывает лишнюю пере-гидратацию (нет цикла, нет дёрганья
  курсора).
- `object_deleted` открытой заметки обработан без краша.
- Подписка снимается при unmount.
- Typecheck Eden зелёный (`bun run typecheck` для desktop или соответствующий
  скрипт). Если есть unit/component-тесты — добавить покрытие логики «remote vs
  own / dirty-guard» (это чистая функция-решение — её МОЖНО и нужно покрыть
  тестом по SDD→TDD: RED → GREEN).
- UI: т.к. полноценная проверка требует 2 машин (СТОП-точка пользователя),
  явно описать в финале, что проверено локально (typecheck/тест логики решения), а
  что требует физического теста. Не объявлять PASS по UI без visual verify.

## Вне scope

- Посимвольный CRDT-merge одновременных правок одной заметки.
- Перфоманс загрузки страниц/кэш (отдельная жалоба, отдельная задача).
