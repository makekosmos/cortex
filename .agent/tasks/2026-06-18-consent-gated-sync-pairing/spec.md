# Spec: consent-gated pairing + merge/replace при подключении устройства

Статус: draft / не начато.
Дата: 2026-06-18.
Автор контекста: расследование sync на macOS (см. раздел 7 — связанные находки).
Контракт CRDT (`protocol.rs`, `types.rs`) — **не трогаем**.

> Этот документ — ТЗ для самостоятельного выполнения позже. Он описывает целевое
> поведение, текущее поведение, дизайн и критерии приёмки. Кода здесь нет.

---

## 1. Проблема и мотивация

Сегодня синхронизация в Kosmos **не соответствует** ожидаемой пользователем
модели «я сам решаю, когда и с кем синхронизироваться».

### Что хочет пользователь (целевая модель)

- Синк появляется **только после явного действия**: я ввёл код подключения
  (или поделился своим) и подтвердил — тогда устройства связаны.
- Никаких автоматических соединений «за моей спиной».
- Не зависит от того, в одной мы локальной сети или нет — код работает
  одинаково (LAN или через интернет, через iroh).
- **Видеть доступные устройства в сети** — список устройств, которые рядом и
  готовы к подключению (как в Syncthing), чтобы можно было предложить им синк,
  а не только вводить код вслепую.
- **Подтверждение на обеих сторонах.** Когда я предлагаю синк — предложение
  появляется и у меня, и у того, кому предлагаю; связь встаёт только после его
  согласия.
- При первом подключении я **осознанно выбираю**, что происходит с данными
  (роли асимметричны, см. §4.3):
  - **Слияние (merge)** — мои и их данные объединяются (CRDT, как сейчас).
  - **Полная замена (replace)** — у меня (инициатора) база становится чистой и
    я забираю себе всё состояние пира (мой случай «синкануться на чистую»).
    Перед этим — бэкап прошлой базы, чтобы можно было откатиться.

> **Фаза.** Сейчас фаза «прокачки в глубину» (надёжность/UX-качество
> существующего синка), а не наращивания новых фич. Эта задача — про глубину:
> сделать синк управляемым и предсказуемым, по образцу Syncthing.

### Что есть сейчас (фактическое поведение, по коду)

Два независимых механизма, и оба не дают consent-gated модель:

1. **LAN-автодискавери — включён по умолчанию, без кода и без согласия.**
   - `platform/runtime/src/main.rs` (~286-320): фоновый `tokio::spawn` при
     старте backend безусловно (если не `KEPLER_SKIP_SYNC=1`) вызывает
     `sync::start_lan_sync(...)`.
   - `platform/runtime/src/sync.rs:71` `start_lan_sync` → RPC `start_sync` с
     `space_id` (по умолчанию `kepler-default`, общий для всех устройств юзера).
   - `core/ark/crates/ark-core/rust/src/main.rs` `handle_start_sync` поднимает
     LAN discovery (`mesh.rs` + `beacon.rs` + `net.rs`) на фиксированном порту
     `LAN_SYNC_PORT = 21531`.
   - **Следствие:** любые два устройства с Kosmos в одной L2-сети и одинаковым
     `space_id` находят друг друга и соединяются автоматически. Именно это юзер
     наблюдал как «подключилось без моего ведома» (ESTABLISHED-сессия с
     `192.168.1.94`).

2. **Код подключения (iroh-pairing) — надстройка, не основной путь.**
   - Окно «Подключить устройство» → `connectWithPairingCode(code)`
     (`platform/desktop/electron/preload.ts:261`) → IPC
     `kepler:settings:sync:connect-with-pairing-code`
     (`platform/desktop/electron/main.ts:1947`) → ARK-операция
     `connect_with_pairing_code`.
   - Свой код — `kepler:settings:sync:get-pairing-code`
     (`main.ts:1924`) → `arkClient.getOwnIrohTicket()` (iroh `NodeTicket`).
   - iroh собран за фичей `iroh-spike` (см. `core/ark/.../Cargo.toml:72`,
     `platform/desktop/scripts/build-backend.mjs` — `--features iroh-spike`).
   - **Проблема:** это работает _параллельно_ авто-LAN, а не _вместо_ него, и
     нет подтверждения на принимающей стороне, нет выбора merge/replace.

Итого: код есть, но он не «ворота» к синку — ворота открыты по умолчанию через
LAN. Нужно перевернуть модель: **по умолчанию закрыто, открывается явным
pairing с подтверждением**.

## 2. Цели

1. **Consent-gated синк.** Устройство **не** синхронизируется ни с кем, пока
   пользователь явно не авторизовал конкретного пира (через код + подтверждение).
2. **Код — основной путь.** Один и тот же flow для LAN и интернета (iroh уже
   так умеет — hole-punch + relay fallback).
3. **Подтверждение на принимающей стороне.** Когда кто-то вводит мой код, я
   вижу запрос «устройство X хочет подключиться» и аппрувлю/отклоняю.
4. **Выбор merge vs replace** при установлении первой связи с конкретным пиром,
   с безопасной (не теряющей данные молча) семантикой.
5. **Видимость устройств** — показывать обнаруженные в локальной сети
   устройства как «доступные для подключения» (Syncthing-style), отдельно от
   уже авторизованных пиров.
6. **Асимметрия merge/replace** — принимающая сторона всегда merge; инициатор
   выбирает merge или replace (с бэкапом своей базы).
7. **Сохранить CRDT-контракт** (`protocol.rs`/`types.rs`) и существующие
   транспорты — менять только _политику установления связи_, не wire-формат.

UX-ориентир: **Syncthing** (явное добавление устройств, подтверждение с обеих
сторон, видимый список устройств/папок).

---

## 3. Не-цели

- Не переписываем CRDT/HLC/version vectors.
- Не выпиливаем LAN/relay/iroh транспорты — меняем только то, _когда_ они
  поднимают коннект к конкретному пиру.
- Не делаем мульти-пользовательский шеринг/права доступа — только устройства
  одного пользователя.
- Не делаем сквозной key-management/identity — переиспользуем существующие
  `device_id` и iroh `NodeId`/тикеты.

## 4. Дизайн (целевое поведение)

### 4.1. Перевести авто-LAN в opt-in

- Ввести понятие **authorized peers** — персистентный список `device_id`
  (+ метаданные: имя, transport, когда авторизован), которым разрешён синк.
- `start_sync` / discovery всё ещё может _слушать_, но **соединение/обмен
  данными с пиром происходит только если пир в authorized-списке**.
  - Вариант реализации: discovery находит пира → если не authorized → не
    рукопожатие данных, а только потенциальный pairing-запрос (или полный игнор
    до явного pairing по коду — решить в open questions §6).
- Глобальный тумблер «Разрешить обнаружение в локальной сети» в настройках
  (по умолчанию — решить: off для чистой consent-модели, либо on-but-gated).

### 4.2. Pairing flow с подтверждением

Сторона A (делится кодом):

1. Открывает «Подключить устройство» → видит свой код (iroh-тикет/код).
2. Backend начинает слушать pairing-запросы для этого кода (ограниченное время /
   до закрытия окна).

Сторона B (вводит код):

1. Вводит код A → backend инициирует pairing-коннект к A.
2. **A получает запрос на подтверждение** («Устройство <имя B> хочет
   подключиться. Разрешить?») + выбор политики данных (см. 4.3).
3. После аппрува A — обе стороны добавляют друг друга в authorized peers и
   начинают синк.

UI: запрос подтверждения — отдельный диалог в shell/настройках; нужен новый IPC
канал `kepler:settings:sync:pairing-request` (push из main в renderer) и
`...:pairing-respond` (approve/deny + policy).

### 4.3. Merge vs Replace — асимметрия ролей

Роли при первом связывании **асимметричны** (так хочет пользователь):

- **Принимающая сторона (тот, кому предложили / кого подключают)** — всегда
  **merge**. Её данные не теряются; в них вливается состояние инициатора
  (которое после его replace может быть пустым — и это ок, тогда у принимающего
  ничего не меняется).
- **Инициатор (тот, кто предлагает / подключается)** — имеет **выбор**:
  - **Merge** — обычное CRDT-объединение по version vectors (ничего не
    теряется, конфликты по HLC).
  - **Replace («забрать всё себе»)** — локальная база инициатора становится
    **чистой**, и он забирает себе полное состояние пира.

Почему это сходится: если инициатор делает replace (обнуляет себя) и пушит
пустоту, принимающая сторона merge'ит пустоту (без изменений), а инициатор
подтягивает полное состояние пира → оба сходятся к данным принимающей стороны.
Никто не теряет данные молча.

Семантика replace, безопасная для version vectors:

- **Обязательный бэкап** локальной `ark.db` перед заменой, **если она есть**
  (паттерн `Kosmos-backup-*`, применявшийся вручную в этом расследовании) —
  чтобы можно было откатиться.
  - Перед заменой — **обязательный локальный бэкап** `ark.db` (см. паттерн
    `Kosmos-backup-*`, который применялся вручную в этом расследовании).
  - НЕ генерировать tombstone-каскад, который сотрёт данные на ДРУГИХ
    устройствах пользователя. Replace — локальная операция «подтянуть всё с
    пира и забыть своё», а не «удалить везде».
  - Технически безопасный путь: фактически то, что юзер делал руками — снести
    локальную `ark.db` и поднять синк с чистого состояния (новый/сброшенный
    version vector), чтобы подтянуть полное состояние пира. См. существующий
    task `.agent/tasks/sync-full-db/` и `fix-sync-not-running-delete/` —
    переиспользовать/сверить с их наработками.
  - ⚠️ Это пересекается с write-boundary: см. `docs-site/concepts/write-boundary.md`,
    `agents/forbidden/ark.md`. Любой Rust-writer в sync-таблицу обязан
    bump'ить version vector (`record_local_upsert/delete`), прямые SQL-writes
    запрещены.

### 4.4. Видимость устройств в сети (Syncthing-style discovery)

Помимо подключения по коду — показывать список устройств, доступных для
синка, чтобы предлагать им подключение из UI, а не только вводить код.

- LAN-discovery (`beacon.rs`) уже знает соседние устройства — нужно **отделить
  "обнаружено" от "авторизовано"**: discovery продолжает находить соседей и
  отдавать их в snapshot как «доступные», но **обмен данными не начинается**
  без явного pairing + подтверждения (§4.1, §4.2).
- В `get_sync_snapshot` добавить раздел `available_devices` (обнаружены, но не
  авторизованы) отдельно от `peers` (авторизованы и синкаются).
- UI экрана «Синхронизация»: блок «Устройства в сети» со списком обнаруженных
  устройств и кнопкой «Предложить синк» → запускает pairing-flow §4.2 (на той
  стороне появляется запрос на подтверждение).
- Приватность: показывать только устройства того же пользователя/пространства;
  не светить произвольные устройства в публичных сетях (решить в §6 — нужен ли
  отдельный identity/ключ пространства, чтобы чужой Kosmos не отображался).
- Для не-LAN (интернет/iroh) discovery-списка нет — там только код. Это ок:
  «устройства в сети» = локальная сеть, код = универсальный путь.

## 5. Критерии приёмки

1. Свежеустановленный Kosmos в общей сети с другим устройством юзера **не**
   синхронизируется автоматически (нет ESTABLISHED без pairing).
2. Pairing по коду работает одинаково в одной сети и между разными сетями.
3. Принимающая сторона видит запрос на подтверждение и может отклонить — при
   отклонении синк не начинается.
4. При первом pairing инициатор выбирает merge или replace; принимающая
   сторона всегда merge; replace делает локальный бэкап и не уничтожает данные
   на других устройствах.
   4a. Экран «Синхронизация» показывает обнаруженные в сети устройства отдельным
   списком «доступные», и предложить им синк можно из UI (без ручного ввода
   кода), с подтверждением на их стороне.
5. После авторизации пары синк идёт автоматически при следующих запусках (не
   надо вводить код заново) — но только с authorized-пирами.
6. Windows-поведение не регрессирует; CRDT wire-формат не изменён.
7. Проверки: `bun run ark:guard:writes`, `bun run ark:smoke`, e2e только с
   `KOSMOS_HEADLESS=1`, ручная проверка pairing Mac↔Windows.

## 6. Open questions (решить в начале реализации)

- Авто-LAN по умолчанию: полностью off, или on-but-gated (слушаем, но без
  данных до authorize)? Влияет на UX «увидеть устройства рядом».
- Где хранить authorized peers и как версионировать (новая sync-таблица vs
  локальный не-синкаемый стор)? Должен ли список authorized peers сам
  синкаться между уже доверенными устройствами?
- Merge/replace — выбор только на принимающей стороне, или согласование обеих?
- Replace через «wipe + fresh pull»: достаточно ли это надёжно для произвольно
  большого состояния пира, и как показывать прогресс/ошибку.
- Срок жизни кода подключения (одноразовый / TTL / до закрытия окна).

## 7. Связанная находка (отдельный баг, не часть этой фичи)

Во время расследования вскрылся **отдельный** macOS-баг supervisor'а, который
надо чинить независимо (иначе синк всё равно не держится на Mac):

- `recoverBackendIfDead("launcher-show")` (`platform/desktop/electron/main.ts:698`)
  → `backendHealthy()` (`main.ts:1096`) пингует backend через
  `commands.list()` с таймаутом **1500 мс**.
- На macOS backend в это время индексирует ~222 приложения, `commands.list`
  не успевает за 1500 мс (`dynamic commands timeout`) → probe ложно решает
  «backend мёртв» → убивает **живой** backend → каскад респавнов
  (`Address already in use 21531`) → `streak 5 → giving up` → синк умирает.
- Ирония: tray-баг 0.5.1 (startup обрывался до `bootInitStarted=true`) случайно
  глушил этот recovery (он no-op без флага). Фикс tray (0.5.4) убрал маскировку
  и обнажил ложный health-check. На Windows не воспроизводится (backend быстрый).
- Предлагаемый фикс (отдельный коммит/bump): сделать health-probe терпимым —
  ретраи с backoff перед вердиктом «мёртв» и/или не гонять recovery во время
  начальной индексации app_index. Лёгкий liveness-ping вместо `commands.list`.

Этот пункт — указатель; чинится вне данной фичи.
