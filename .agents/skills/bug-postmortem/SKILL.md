# bug-postmortem

Стандартный workflow для bug fix задач в Kosmos. Цель: каждый исправленный баг оставляет след в `docs-site/agents/postmortems.md` так, чтобы будущий ты (или другой агент) не наступил на те же грабли.

## Когда применять

- Пользователь сообщил о баге («что-то по пизде пошло», «сломалось», «не работает», «зависло»)
- Задача формулируется как «почему X не работает» / «почини Y»
- Прежде чем PASS — обязательно постмортем

**НЕ применять для:** новых фич, рефакторинга, косметики, опечаток. Постмортем — про неожиданное поведение, не про планируемые изменения.

## Workflow (5 шагов)

### 1. Воспроизведи и пойми root cause

- Прочитай логи (`%APPDATA%\Kosmos\logs\kepler-backend.<date>`, `%APPDATA%\Kosmos\logs\kepler-shell-<date>.log`).
- Найди точное место в коде (`file:line`).
- Сформулируй **почему** это произошло на уровне «не угадаешь без stack trace». «Забыл проверить null» — плохо. «NTFS scanner возвращает один path через два root'а из-за junction'а, INSERT валит транзакцию по PK» — хорошо.
- Если корневая причина не установлена однозначно (например, нет stderr capture) — **зафиксируй это явно**. Не выдумывай.

### 2. Сделай запись в постмортемах **ДО** фикса

Открой `docs-site/agents/postmortems.md`, добавь блок сверху (под шаблоном). Формат:

```markdown
## YYYY-MM-DD — короткое название

**Симптомы.** Что наблюдал пользователь, 1–2 предложения.
**Где жило.** `file:line` ссылки.
**Root cause.** Почему именно так, не на уровне симптома.
**Fix.** TBD (заполнится после).
**Регрешн-защита.** TBD.
**Prevention.** TBD.
```

Этот шаг **обязателен до фикса** — иначе после починки сложно вспомнить контекст и пишется на отъебись.

### 3. Напиши регрешн-тест **ДО** фикса

- Тест воспроизводит баг (падает на текущем main).
- Тест простой: меньше моков, ближе к unit-уровню. Если возможно — на той функции, где баг.
- В комментарии теста — ссылка на дату и краткое описание: `// Regression: YYYY-MM-DD. <короткое описание>`.
- Rust: добавляй в существующий `#[cfg(test)] mod tests` соответствующего модуля.
- TS: рядом с исходником (`*.test.ts`).

Запусти. Убедись что **тест падает на сломанной версии** (если возможно — закоммить тест отдельно перед фиксом, иначе хотя бы локально проверь reverted-fix).

### 4. Сделай минимальный фикс

- Минимум diff. Никакого попутного рефакторинга (правило из CLAUDE.md).
- В коде — короткий комментарий с **WHY**, ссылающийся на постмортем: `// См. postmortems.md § YYYY-MM-DD.`
- Прогон guard'ов перед коммитом:
  - Rust: `cargo test -p <crate> <test_name>`
  - Изменения в data-слое: `bun run ark:guard:writes`
  - Substantial: `bun run ark:smoke`
  - Docs: `bun run docs:check` + `bun run docs:sync` если правил `docs-site/`

### 5. Дополни постмортем **после** фикса

Вернись в `docs-site/agents/postmortems.md`, заполни `**Fix.**`, `**Регрешн-защита.**`, `**Prevention.**`. Самое важное — **Prevention**. Это не «было плохо, стало хорошо» — это **общий вывод**, на что обращать внимание в похожих случаях. Примеры хороших prevention-нот:

- «Любой bulk-insert по сырым данным из внешнего источника обязан дедупиться перед INSERT.»
- «`std::sync::Mutex` в долгих транзакциях, вызываемых из async task'а — анти-паттерн. Используй `spawn_blocking` или отдельный thread.»
- «Supervisor должен делать health-check WS, а не только pid-alive.»

Плохой prevention: «нужно тестировать лучше», «нужно быть внимательнее».

## После завершения

- Закоммить **одним коммитом**: фикс + тест + postmortem entry + (если нужно) sidebar update.
- Сообщение: `fix(<scope>): <short> + postmortem`.
- Если фикс substantial (несколько файлов / новая абстракция) — создай ещё `.agent/tasks/<DATE>-<slug>/` proof loop с evidence (см. `docs-site/concepts/proof-loop.md`).

## Что НЕ делать

- ❌ Описывать постмортем **после** фикса по памяти. Контекст теряется, формулировки становятся ленивыми.
- ❌ Писать в постмортем «починили баг, всё работает». Это **не** prevention. Запиши **почему** баг был возможен и **что** нужно изменить в подходе, чтобы класс таких багов отсекался заранее.
- ❌ Пропускать регрешн-тест. Без него запись в постмортеме — пустая бумажка.
- ❌ Создавать отдельный файл `postmortem-YYYY-MM-DD.md`. Все записи живут в одном `docs-site/agents/postmortems.md`. Свежие — сверху.
- ❌ Удалять старые записи. Журнал растёт. Если запись устарела — добавь подзаголовок «UPDATE YYYY-MM-DD: …», не удаляй.
